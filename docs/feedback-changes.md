# 계획서에서 바뀐 점 (피드백 반영)

계획서를 내고 나서 받은 피드백으로 화면 구성을 두 군데 고쳤다.
무엇을 왜 바꿨는지 남겨 둔다.

---

## 1. 메인 화면에 달력을 넣었다

**받은 피드백** — 내가 어떤 서비스를 쓰는지 한눈에 볼 수 있는 달력이 있으면 좋겠다.

**왜 맞는 말인가**
계획서 스케치에는 `월 2회`, `월 26회`처럼 **횟수만** 있었다.
그런데 이 앱이 하려는 건 "생활 습관을 분석하는 것"인데, 횟수만으로는
*얼마나* 쓰는지는 알아도 *언제* 쓰는지를 알 수 없다.
달력을 넣으면 "주말에만 몰아본다", "결제일 지나고 2주째 손도 안 댔다" 같은
**패턴**이 눈에 들어온다. 계획서 2번 처리 항목에 적어 둔
"주 이용 요일·시간대를 계산한다"를 화면으로 꺼낸 셈이다.

**어떻게 만들었나**
한 칸(하루)에 두 가지를 같이 표시한다.

| 표시 | 뜻 |
| --- | --- |
| 색 점 | 그날 이용한 서비스 (색은 카테고리별) |
| `₩` 배지 | 그날 결제되는 구독 |

둘을 같이 둔 이유: 돈이 나가는 날과 실제로 쓴 날을 나란히 놓아야
"15일에 17,000원이 빠져나갔는데 그 주에 한 번도 안 봤네"가 보인다.
이게 이 앱이 하고 싶은 말이다.

날짜를 누르면 그날 쓴 서비스를 켜고 끌 수 있어서,
계획서 Input의 '이용함' 버튼 입력이 들어가는 자리이기도 하다.

> **정한 것**: 점 색깔은 서비스가 아니라 **카테고리**에 붙였다.
> 서비스마다 색을 정하면 서비스를 추가할 때마다 색을 새로 골라야 해서
> "행만 추가하면 된다"는 원칙이 깨진다. 카테고리는 6개로 고정이라 괜찮다.

## 2. '이번 달 진단'을 누르면 상세 화면으로 간다

**받은 피드백** — 어떻게 분석했고 절약 최대 예상액이 어떻게 나왔는지를
더 보여주는 화면으로 넘어가면 좋겠다.

**왜 맞는 말인가**
원래 화면은 `당신은 "방치형"`, `절약 예상 최대 −28,900원`이라는
**결론만** 툭 보여 줬다. 사용자 입장에서는 이 숫자를 믿을 이유가 없다.
게다가 이 앱에서 가장 중요한 부분(계획서 IPO의 **Process**)이
화면에 하나도 안 드러나 있었다.

**어떻게 만들었나**
`/diagnosis` 화면을 만들어 계산 순서를 ①~⑤로 나눠 보여 준다.

| 단계 | 보여 주는 것 |
| --- | --- |
| ① | 이번 달 이용 횟수를 어떻게 셌는지 (달력 기록 / 몰아 입력 / 실제 쓰는 값) |
| ② | `17,000원 ÷ 3회 = 5,667원` 처럼 나눗셈 식 그대로 |
| ③ | 해지 후보를 고른 기준과, 구독마다 왜 걸렸는지 |
| ④ | 절약 예상 최대액을 만든 덧셈 |
| ⑤ | 습관 유형 판정 규칙 표와, 내가 어디에 걸렸는지 |

이렇게 하려고 `src/lib/analyze.ts`가 답만 돌려주지 않고
**판단 이유(`reason`)와 기준(`criteria`)까지 같이** 돌려주도록 만들었다.

## 이 과정에서 내가 직접 정한 기준들

계획서 6번에 "정답이 없는 판단은 근거를 적어 두겠다"고 썼는데,
실제로 세 군데에서 그런 판단을 해야 했다.

| 정한 것 | 값 | 근거 |
| --- | --- | --- |
| 1회당 비용 기준선 | **3,000원** | 편의점 커피 한 잔 값. "한 번 쓰는 데 커피 한 잔 값을 낼 만한가?"라고 스스로 물어볼 수 있는 크기라서 골랐다. `COST_PER_USE_LIMIT` 하나만 고치면 화면 전체가 따라 바뀐다. |
| 이용 횟수 0회 처리 | 나눗셈 대신 **'계산 불가'로 따로 표시** | 0으로 나누면 무한대가 나온다. 억지로 큰 숫자를 만드는 대신, 0회는 "한 번도 안 썼다"는 **가장 강한 해지 신호**로 보고 목록 맨 위에 따로 올렸다. |
| 달력 기록과 몰아 입력이 둘 다 있을 때 | **몰아 입력을 우선** | 몰아 입력은 "날짜는 기억 안 나는데 이만큼 썼다"는 뜻이라 더 나중에, 더 정확하게 알려 준 값으로 봤다. 대신 화면에 `(몰아 입력)`이라고 반드시 표시해서 어느 값을 쓰는지 숨기지 않았다. |

## 차시 계획은 어떻게 되나

계획서의 차시 구성 자체는 그대로 두고, 차시 3~5에서 만들 화면이 두 개 늘어난 셈이다.

| 차시 | 원래 계획 | 지금 상태 |
| --- | --- | --- |
| 2 | 메인 화면 뼈대 | 끝 (+ 달력 추가) |
| 3 | 구독 등록 폼 | 끝 — `/subscriptions/new` |
| 4 | 이용 기록 입력 | 끝 — 달력에서 날짜별 입력 + `/usage` 몰아 입력 |
| 5 | 처리 로직 · 결과 화면 | 1회당 비용·해지 우선순위·습관 유형까지 끝. **대체 서비스 추천은 아직** |
| 6~8 | Supabase | 아직 |

**아직 안 만든 것**

- 대체 서비스 추천 화면 (계획서 스케치 4번: 같은 카테고리에서 더 싼 서비스 비교)
- 요일별 이용 패턴 막대그래프
- 저장: 지금은 브라우저(localStorage)에만 저장된다. 차시 7에서 `src/lib/store.ts`의
  함수 속만 Supabase 호출로 바꾸면 화면 코드는 거의 그대로 쓸 수 있게 분리해 두었다.
